# Batch 381–400

This batch introduced one localization architecture and controlled data interoperability.

Warka supports `en`, `am`, and `om`, with English fallback for noncritical missing text. Catalog keys translate application chrome and controlled display labels while API enums, identifiers, and user-authored content remain unchanged. Locale and Gregorian/Ethiopian calendar preferences are independent. Ethiopian dates are display and input assistance; canonical database and API dates remain Gregorian timestamps or ISO dates.

External references retain Warka primary identity and are unique only within source system and entity type. They never trigger automatic merging. School or organization scoped source profiles contain validated CSV/XLSX mappings. XLSX parsing requires an available, clean scanned asset, rejects formulas, and enforces file, sheet, row, column, and cell limits.

Student mapping exposes an approved field catalog. Transformations are deterministic data operations without JavaScript, SQL, shell, network, or user regex execution. Dry runs write no official domain records and record exact file, profile, mapping, and transformation checksums. Possible duplicates require human review. Application claims one successful exact dry-run version transactionally, creates draft enrollments, and does not approve enrollment, verify guardians, provision accounts, or merge students.

The Warka-native `studentTransferPackage` exchange format uses a versioned manifest, bounded safe file names, and SHA-256 checksums. It includes only fields approved by the existing transfer workflow. It is not a database dump and makes no claim of compatibility with a government or external standard.
