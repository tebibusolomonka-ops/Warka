# Batch 421–440: deployment reliability

Warka now ships multi-stage, non-root API and static web containers behind a Caddy TLS gateway. The provider-neutral single-host Compose topology keeps PostgreSQL private, stores database, uploads, and backups in persistent volumes, and accepts an external-services hosting profile.

Migrations run in a dedicated one-shot container before the API. Approved sensitive settings may be read from bounded text secret files. Liveness stays separate from bounded startup and readiness checks; unavailable scanners continue to fail uploads closed.

A repository semantic version feeds API and browser metadata plus OCI labels. Versioned deployment manifests bind release, revision, images, migration compatibility, profile, and build time without secrets. `DeploymentRecord` stores safe operational history, while health gates require readiness, migration, version, scheduler, and worker recovery facts.

Rollout and rollback commands require explicit environment or review acknowledgement and support mutation-free dry runs. Rollback selects a known manifest, refuses blocked compatibility, never reverses database migrations, and reruns health checks. Operations presents release history and rollback eligibility as a read-only operator view.

CI validates image builds, Compose, Caddy, release metadata, manifests, checksums, security output, and synthetic rollout and rollback policy. Local smoke tests require an explicit target and perform read-only requests.
