# Batch 361–380: recovery and performance reliability

Warka now preserves interrupted scheduled executions and reconciles each supported domain according to its side effect risk. Leases and bounded heartbeats identify ownership loss. Safe tasks become explicitly retryable, ambiguous email delivery is held for provider reconciliation or an operator decision, scans remain unavailable until a clean result, and restore rehearsals require review rather than blind replay. `RecoveryReview` provides a controlled, audited workflow. Disaster recovery readiness reports current backup, verification, rehearsal, scheduler, and storage evidence without promising recovery success.

Performance telemetry retains broad request and query categories, duration, failure, slow query, and budget warning counts. It never retains SQL text, query parameters, personal identifiers, or request IDs as labels. Reviewed indexes support actual scheduler, outbox, enrollment, coursework, and student search paths. Frequently changing delivery lists use stable timestamp and ID cursors; request timeouts vary by work category and exclude file streams; bounded database pool settings are centralized.

The load harness requires an explicit target and environment acknowledgement, uses synthetic fixture identifiers, and blocks production by default. Baseline scenarios are read only. Operations users can inspect safe recovery and performance summaries; ordinary school roles cannot access them. CI validates load configuration without generating sustained traffic.
